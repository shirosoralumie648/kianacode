## 关键决策

### 决策 1：工作区改动处理策略

**选择**：逐文件 commit（审查通过后），不 stash 全部

**理由**：
- 注释改动通过审查就可以 commit
- 保持工作区相对清洁
- 更清晰的 git 历史（知道什么时候什么文件完成的）

**执行**：
```
每个文件：注释 → 格式检查 → 编译检查 → 质量审查 → 通过 → git commit
```

### 决策 2：统计口径确认

**定义**：只有"已通过"级别才计入"已验证完成"

**理由**：
- 防止过度乐观的完成度声称
- 确保每个计数都能追踪到具体文件和审查结果
- 符合"真实就是唯一的胜利"原则

### 决策 3：标准统一

**Batch 1-2 的标准作为金标准**，Batch 3+ 按相同标准评审

**理由**：
- 避免质量滑坡
- 新人容易对齐
- 降低审查的主观性

## 教训与建议

### 本工程的三个关键认识

1. **统计口径要明确**
   - 不能混用"有注释"和"深度处理"
   - 要有明确的"什么时候算完成"的定义
   - 避免虚报进度

2. **注释工程需要工作流**
   - 不是"写完就完"
   - 需要"注释 → 审查 → 修改 → 提交"的闭环
   - 质量关卡很重要

3. **工作区管理很关键**
   - 281 个改动文件不可能同时处理
   - 逐文件流程化提交是关键
   - 每个提交都要能单独验证

### 如果继续做下去

1. **保持标准一致**
   - 后续新人对标 Batch 1-2
   - 如果发现标准太严，调整时要文档化
   - 不要"新人的注释标准松一点"

2. **定期同步进度**
   - ANNOTATION_TASK_MANIFEST.md 每周更新
   - 保持表格的精确性（是关键依赖）

3. **收集反馈**
   - 问问使用者：注释是否有用
   - 如果好用，保持风格；不好用，改进标准

4. **考虑自动化**
   - 某些注释（比如类型文档）可能可以生成
   - 某些审查（比如覆盖度）可能可以脚本化
