### 三个核心概念

#### 1. 注释状态机（8 级）

```
未处理 → 扫描中 → 注释中 → 待审查 → 审查中 → 已通过 → 有待改进 → 已提交
                                                  ↑                    ↑
                                             质量关卡              GIT 关卡
```

**只有"已通过"才计入完成度**。

#### 2. 深度处理定义

**深度处理** = 满足以下全部条件：
- ✅ 模块级说明：顶部文档化
- ✅ 结构体/枚举：字段级注释
- ✅ 函数级：参数、返回值、用途说明
- ✅ 逻辑块：条件分支、循环、状态转移有块注释
- ✅ 特殊语法：async/unsafe/trait 有说明
- ✅ 编译+格式检查通过
- ✅ 独立质量审查通过

#### 3. 优先级路线图（P1-P4）

| 优先级 | 范围 | 理由 |
|--------|------|------|
| **P1** | 关键路径（dispatch, lifecycle, harness, tools） | 影响核心执行模型 |
| **P2** | 存储层（event_store_core, journal_core, jsonl） | 影响数据持久化 |
| **P3** | 外围能力（provider, query, skills） | 影响集成和观测 |
| **P4** | 入口与可选（cli, web, mcp, tui） | 影响用户交互 |

## 📝 工作流（标准作业程序）

### 第 1 步：选择文件

从 ANNOTATION_TASK_MANIFEST.md 中选择：
- 状态为"未处理"或"需要深度处理"
- 优先级最高的
- 依赖关系最少的

**建议粒度**：200-500 行源码

### 第 2 步：扫描（15-30 min）

```bash
# 1. 通读源码，理解：
#    - 这个模块做什么
#    - 有哪些主要类型
#    - 有哪些关键函数
#    - 复杂度在哪里

# 2. 找到：
#    - 函数签名
#    - 结构体/枚举定义
#    - 复杂的条件分支、循环、状态转移
#    - 特殊语法（async/unsafe/trait impl）
#    - 错误处理
#    - 常数和 Magic number

# 3. 记下"这个地方需要注释"
```

### 第 3 步：注释（60-180 min，取决于复杂度）

按以下顺序添加注释：

**层级 1：模块顶部（如果没有）**
```rust
//! 【模块职责】
//! 这个模块做什么、在系统里的位置、与其他模块的关系
//!
//! 【关键概念】
//! 如果有特殊的术语或设计意图，在这里说清楚
```

**层级 2：类型定义**
```rust
/// 【结构体用途】
/// 这个 struct 代表什么，什么时候会创建、什么时候会用
pub struct Foo {
    /// 【字段用途】
    /// 这个字段存什么、为什么要存、从哪来的
    bar: u32,
}
```

**层级 3：函数签名**
```rust
/// 【函数用途】
/// 这个函数做什么、什么时候该调它
///
/// # Arguments
/// * `x` - 【参数含义】什么、为什么需要、有什么约束
///
/// # Returns
/// 【返回值含义】什么、什么时候为 Some/Ok/Err
///
/// # Panics / Errors
/// 【错误情况】什么情况下会失败、为什么、如何处理
pub async fn do_something(x: u32) -> Result<String, Error> {
```

**层级 4：复杂逻辑块**
```rust
// 【块目的】为什么做这个判断、不同分支的后果
if condition {
    // 【分支 A】当 condition=true 时做什么、为什么
    action_a();
} else {
    // 【分支 B】当 condition=false 时做什么、为什么
    action_b();
}
```

**层级 5：特殊语法**
```rust
// 【SAFETY】
// 为什么这个 unsafe 是安全的、什么前置条件必须满足
unsafe { /* ... */ }

// 【Async】
// 这个 await 的任务关系、是否会阻塞、取消语义
await_something().await

// 【Trait impl】
// 为什么要实现这个 trait、这个实现的语义
impl MyTrait for MyType { }
```

### 第 4 步：验证（10-15 min）

```bash
# 1. 格式检查
cargo fmt --check -p <crate>

# 2. 编译检查
cargo check -p <crate>

# 3. 差异审查
git diff <file>  # 确认只有注释改动，没有代码逻辑改动

# 4. 状态更新
# 在 ANNOTATION_TASK_MANIFEST.md 中把文件状态改为"待审查"
```

### 第 5 步：质量审查（20-60 min，取决于复杂度）

**审查员职责**：以只读方式检查注释质量

检查清单（来自 ANNOTATION_TASK_MANIFEST.md）：
- [ ] 注释解释了内部逻辑，不只是表象
- [ ] 变量定义说明了数据来源和用途
- [ ] 条件分支说明了判断目的和后果
- [ ] 循环说明了处理范围和终止条件
- [ ] 函数调用说明了参数如何构造、结果如何使用
- [ ] async/await 说明了任务关系
- [ ] 并发代码说明了锁、信号、共享状态
- [ ] unsafe 块有 SAFETY 注释说明内存条件
- [ ] 错误处理说明了来源、路径、恢复
- [ ] 状态机说明了转移条件
- [ ] 没有机械重复的无信息量注释
- [ ] 所有注释有源码依据，没有未确认的推断
- [ ] 特殊情况和边界情况被涵盖

**结果**：
- ✅ 通过 → 状态改为"已通过"，准备 commit
- ❌ 需改进 → 状态改为"有待改进"，反馈给注释者修改
- 如果需要 2 次循环还不通过，可标记为"已通过（有保留）"并手工介入

### 第 6 步：提交（5 min）

```bash
# 1. 最后格式检查
cargo fmt --all --check

# 2. 创建 commit
git add <file>
git commit -m "docs: 注释 <file> —— [简要说明职责]"

# 3. 更新清单
# 在 ANNOTATION_TASK_MANIFEST.md 中把文件状态改为"已提交"
```

## 🔍 常见问题

### Q1：怎么区分"有注释"和"深度处理"？

**有注释**：只要代码行旁边或上方有 `//` 或 `///`  
**深度处理**：满足本指南第 3 步"注释"中的所有 5 个层级

### Q2：注释可以有多长？

**没有硬限**，但遵循"信息量至上"：
- 简单代码：1-2 行块注释就够
- 复杂逻辑：3-5 行解释清楚为止
- 不要写"这行创建一个 Vec"这种废话

### Q3：可以修改代码逻辑吗？

**严格禁止**。本工程只添加注释，不改行为。

如果发现 Bug 或改进机会，在"备注"中记录，不在本任务中修复。

### Q4：上下文压缩后怎么恢复进度？

1. 读 `docs/code-guide/ANNOTATION_TASK_MANIFEST.md`（关键表格）
2. 检查 `git status` 找当前改动
3. 根据优先级和前置依赖决定下一批工作
4. 从优先级最高的未处理文件开始

### Q5：我是新人，应该从哪个文件开始？

建议顺序（从难到易）：
1. 阅读 Batch 1 的 `kiana-core/src/authority.rs`（参考标准）
2. 查看 Batch 2 的 `kiana-eventlog/src/writer_queue.rs`（另一个风格）
3. 选择一个 P1 中的小文件试手（<300 行）
4. 让别人审查一遍，根据反馈改进风格
5. 然后处理更复杂的文件

### Q6：质量审查应该由谁做？

**理想**：与注释者不同的人（独立视角）

**实际**：如果人手紧张，可以：
- 注释者自己做一遍自审
- 再请别人核检
- 如果 2 个人都通过，就算过了

### Q7：Batch 1-2 vs Batch 3，标准一样吗？

**完全一样**。这就是为什么要建立"标准"。

如果 Batch 3 的注释达不到 Batch 1 的水准，就不通过审查。
