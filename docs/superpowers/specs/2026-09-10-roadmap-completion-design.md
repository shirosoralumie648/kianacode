## 1. 问题

`docs/roadmap.md` 现在覆盖 30 个步骤（`0.1`–`8.2`），映射到实施切片 A/B/F/G/H 的一小块，约等于 canonical 阶段 P0 的前半。用户目标是：**照这份文档就能做到完全符合设计文档的产品**。

设计面体量：

| 项 | 数量 | 来源 |
|---|---|---|
| canonical 阶段 | P0–P6 | `company-os-spec-index.md` §7 |
| 实施切片 | 13（A–M） | 同上 |
| 实施单元 | **38**（A–I 共 9 + J1–J8 + K1–K8 + L1–L6 + M1–M7） | `company-os-implementation-outline.md` §3 |
| 能力域 | 6（Coding / Office / Search / Commerce / Mobility / Home） | `company-os-implementation-outline.md` §4 |

因此"补全"不是给一份清单追加条目，而是把 roadmap 从**审计 backlog 的附属清单**提升为**产品计划的骨架**。

### 1.1 已发现的四处缺口

1. §9（P5/P6）是空壳，5.1–6.3 只有一行"详细卡见审计文档"。
2. 审计 backlog 的 P2 三条（checkpoint/fork/compaction、observability receipts、multi-agent composition）完全未进表。
3. 8.x（审计刷新）在 §1 表里有行，却没有对应小节。
4. 在飞状态过时（CI 结果、未提交的 1.1 改动未回填）。

### 1.2 已发现的三套 P 编号冲突

| 来源 | P 的含义 | 处置 |
|---|---|---|
| `reference-agent-audit/00-unified-agent-flow.md` | 审计优先级 P0/P1/P2 | 改称「审计优先级」，不再用 P 编号 |
| `docs/roadmap.md` §4–§10 | 自造 P0–P7 | 全部作废 |
| `docs/company-os-spec-index.md` §7 | **唯一 canonical** P0–P6 | 保留，作为总图骨架 |

同一份文档里 `§5 P1 — 账本与恢复` 与 canonical `P1 ContextPlan/Memory/Cache` 指两件事，读者照任一份都能"有理有据地做错"。补全的首要动作是消灭第二、第三套编号。

## 4. 总图与编号

### 4.1 编号规则

- 形式 `P<阶段>-<切片>-<序号>`，例 `P0-A-01`、`P0-G-02`、`P1-J2-01`。
- 切片字母用 `implementation-outline` 的 A–M；子切片用 `J1`…`M7`。
- 一个切片在同一阶段可以有多个单元（如 `P0-G-01`…`P0-G-04`）。**38 个切片/子切片是覆盖下限，不是行数上限。**
- 序号按该切片在**该阶段内**的依赖顺序排，不预留空号。
- 单元编号**永不重编**；拆分单元加后缀 `-a`/`-b`，不重排后续编号。

### 4.2 总图列

`编号 | 阶段 | 切片 | 依赖 | 退出条件 | 状态`

### 4.3 状态口径（防第二真相）

- 总图状态只是**索引**；唯一证据仍是 `CURRENT_STATUS.md` 的证据块。
- 每个 ✅ 必须绑定三件：提交哈希 + CI run id + 证据块名；缺一即降为 ⏳。
- 图例沿用现有六档：✅ 🔄 ⏳ ❓ 🚫。

## 5. 卡片模板

````markdown
### P0-G-02 账本记录可重放 history　🔄

- **现状**：账本不记 user prompt，也不记 provider 的 tool_call_id（`lifecycle.rs:40-54`）。
- **做什么**：新增 `run.prompt` / `run.tool_call` / `run.tool_result` 事件 kind，全部过 `redact_event_value`。
- **风险**：新事件增加 append 次数，必须沿用 0.1 的合并语义。
- **验收**：`resume_rebuilds_model_visible_history_from_ledger`
- **依赖 / 边界**：依赖 `P0-A-01`；不新增模型可见工具，不动 `PROTOCOL_SCHEMA`。
- **依据**：`company-os-implementation-outline.md` §Slice G
````

### 5.1 硬规则

1. 「依据」必须指向 canonical 文档章节；roadmap **不定义新规范**（沿用它自己的开篇声明）。
2. 每张卡**最多 8 行**；写不下去说明该拆单元。
3. 「验收」必须是一个可写成测试名的断言，不能是"完成 XX"这类描述。

## 7. 补全完成的定义

1. §1 总图**覆盖全部 38 个实施单元（切片/子切片）**，每个单元至少一行，每行都有编号、阶段、切片、依赖、退出条件、状态；一个单元在同阶段拆成多步时按 `-01`/`-02` 顺延，行数可多于 38。
2. P0–P4 的每个单元都有一张六行卡，且「依据」能点到 canonical 章节。
3. 没有任何**编号**同时出现在两个阶段。切片可以跨阶段出现（如 J7 在 P0 有流式基线单元、在 P4 有协议单元），但每个编号只属于一个阶段。
4. 旧编号（`0.x`–`8.x`）在全文档中不再出现。
5. 三套 P 编号只剩 spec-index 一套。

## 8. 不在范围内

- 不为 P5/P6 写六行卡（只登记边界与"为什么不现在写"）。
- 不修改任何 canonical 规范文档（`company-os-*.md`）。
- 不修改 `CURRENT_STATUS.md` 的证据块（除新增本设计对应的证据块）。
- 不在本设计中决定 `7.1` 第二执行循环的处置（属 §10 待拍板项）。

## 9. 风险

| 风险 | 缓解 |
|---|---|
| roadmap 变长后与 canonical 文档重复甚至冲突 | 硬规则 1：只引用、不定义；每卡必带「依据」 |
| 总图状态被当成证据 | 状态口径：✅ 必须绑定提交 + CI + 证据块，否则 ⏳ |
| 38 个单元的 P0–P4 归属有争议 | 归属以 `spec-index` §7 与 `implementation-outline` §7 为准；争议项标 ❓ 并列出两种归属 |
| 补全过程本身拖住开发 | 先补总图 + P0 卡，其余阶段按阶段分批补 |
